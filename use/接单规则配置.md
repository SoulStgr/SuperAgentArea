# 接单规则：配置方式与实现逻辑

> 适合操作者与二次开发：说明「接单规则」（Policy rules）现在怎么配、配完发生什么，以及它和准入名单、工作站、工单之间的关系。
> 术语与领域模型见 [docs/001-domain.md](../docs/001-domain.md)、[docs/002-authorization.md](../docs/002-authorization.md)，完整架构见 [docs/007-architecture.md](../docs/007-architecture.md)。

## 1. 接单规则是什么

接单规则回答一个问题：**一个主动候选（proactive candidate）值不值得变成工单。**

它不是硬性权限。真正决定“谁能发起工作”的是两层前置门禁：

1. **来源侧过滤**：这个来源是否监听该会话/仓库/地址；
2. **Policy 准入**：发送人是否在 allowed 名单、admission 表对该接收范围给出 explicit/inferred/ignore、机器人是否在 bots 名单、是否重复。

规则只在候选通过上述门禁、进入主 Session 研判时使用。规则不能绕过 allowed、admission、Mandate 或工具权限；它只决定“这件事是否属于我们愿意主动接的工作类型”。

显式请求（allowed 名单里的人直接 @/私聊机器人）不经过规则判断，由主 Session 按 dispatch 决定直接回答、接单或反问建站。规则主要约束**主动/推断候选**。

## 2. 默认五条规则

| id | 名称 | 用途 |
| --- | --- | --- |
| `workstation-work` | Workstation work / 站内明确工作 | 已有工作站内的具体改动、文档、配置、文案、视觉等可验收交付 |
| `new-workstation` | New workstation / 新工作站任务 | 明确的新项目/新工作站长期工作；缺少名称或地址时由 host 反问触发者，不自行编造 |
| `investigation` | Investigation / 排查评审 | 排查、诊断、评审、分析并给出结论，产出是分析报告而不是代码 |
| `one-off-task` | One-off task / 一次性任务 | 有明确结束点的一次性工作，落在 workspace，不新建工作站 |
| `casual-chat` | Casual chat / 闲聊 | 问候、小聊、天气、感谢、询问“你能做什么/怎么用”等日常对话：**直接回复，不建工单、不建工作站** |

`casual-chat` 只负责日常沟通；一条消息如果同时包含具体工作，仍会按对应工作规则判断。规则是模型可见的说明文本，不是脚本分支。

## 3. 配置位置

### 3.1 每个来源实例一份（面板）

1. 打开 **设置 → 工单源**，选中某个来源类型；
2. 在该账号行点 **策略提示配置**（或来源详情页的入口）；
3. 切到 **策略**；
4. 在 **接单规则** 里新增、编辑、启用/停用、删除、拖动排序；
5. 点 **保存**。

没有保存过自有规则的来源显示 **继承自安装默认**；保存后它就有自己的一份规则，之后安装默认再改也不会自动覆盖它，直到你把它改回继承（目前通过管理 API 或重新设置为默认五条来统一）。

### 3.2 安装默认（不经过面板规则编辑器）

面板没有单独的“全局规则”编辑页；安装默认保存在 settings 的 `policy` 块。管理 API 可以直接读写：

```http
GET /orchestrator/api/settings
// blocks.policy.value.rules = 安装默认规则

PUT /orchestrator/api/settings/policy
{
  "value": {
    "rules": [ /* 五条规则 */ ],
    "sources": { /* 每个来源的 allowed/admission；不要在这里放 rules */ }
  },
  "revision": 3
}
```

每个来源自己的规则走独立块：

```http
PUT /orchestrator/api/settings/policy:<sourceInstanceId>
{
  "value": {
    "allowed": [],
    "admission": {},
    "rules": [ /* 这个来源自己的规则 */ ]
  },
  "revision": 1
}
```

请求需带 `x-orchestrator-request: 1`（同源管理 API 的约定）。保存使用乐观并发：`revision` 过期会返回 409，先重新读再保存。

### 3.3 字段含义

每条规则只有四个字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定标识，匹配与 Mandate 记录用；只能包含字母、数字、`_`、`-`，最长 80 |
| `name` | 面板/提示词里显示的名称，最长受 `LIMITS.ruleName` 限制 |
| `enabled` | 停用的规则不参与研判，也不会被要求评估 |
| `instruction` | 给模型看的条件说明；写清“接什么、不接什么、需要什么证据”；可写流程/沟通要求（如要求谁 review PR） |

规则不要写成硬编码路径或命令；它们是给模型判断的说明。真正不能越过的限制请放到 allowed、admission、Mandate、工具权限或团队提示词里。

## 4. 保存之后发生什么

1. 保存会生成新的 **Policy version**（由安装默认规则、各来源规则、准入表、accept mode 组合计算）。
2. 正在运行的 Eval 会作废并按新版本重新排队。
3. 受影响的进行中工单会收到 policy-changed Input，说明命中的规则变了/授权人失效/主动接单不再允许等；不会被立即撤销 Mandate，但下一次恢复/重校验会按新规则。
4. 每个来源的自己的规则只影响该来源的工单和候选；安装默认变化会影响所有仍继承默认的来源。
5. 配置历史（设置页的“配置历史”）会记录规则新增/改名/条件/启停/删除，以及凭据的“已设置/已更换/已清空”（不显示内容）。

## 5. 一次接单的完整链路

```text
来源事件
  → Source 过滤（监听范围、机器人/自己消息、去重）
  → Gate（不调模型）：allowed + admission 表 + bots + follow-up
  → 候选（proactive 或 explicit）
      ├─ explicit：主 Session 按 dispatch 直接回答 / 接单 / 反问建站
      └─ proactive：Eval 研判
            ├─ 对“这个来源当前生效的规则”逐条给出 matched/未命中
            ├─ accept 需要至少一条命中 + 方向确定 + intent_evidence
            ├─ observe 模式：只记“本会接单”，不建单
            └─ auto 模式：命中规则才建单
  → Decision + Mandate（记录 Policy version、命中规则 id、授权人/范围）
  → 工单 worker 读该来源的规则名称/指令（以及工作站要求）
  → 结果交付
```

与工作站的关系：

- 规则决定“值不值得接”；
- ProjectService 决定“归到哪个工作站/是否 workspace/是否反问建站”；
- 新工作站不会因为规则命中就静默创建；缺少名称/地址时走 `needsProject` 反问，触发者确认后才建。

## 6. 常见配置示例

### 6.1 只接已有工作站的代码/文档改动

只启用 `workstation-work`，其余停用。适合希望严格控制主动接单范围的团队。

### 6.2 允许新项目，但必须触发者确认

启用 `new-workstation` + 需要的 `workstation-work`。新项目规则只把请求带入反问流程，真正的创建仍由触发者在会话里回答（或面板回答）。

### 6.3 日常对话直接回复

保持 `casual-chat` 启用。问候、天气、感谢、能力询问会直接回复；如果消息同时有具体工作，会按工作规则另行判断。

### 6.4 来源差异

- GitHub 来源：一般只开 `workstation-work`/`investigation`；
- QQ/微信/钉钉：可以开 `casual-chat` + 工作规则；
- 网页/地址来源：通常只开 `investigation`/`one-off-task`，避免把普通资讯当工作。

每个来源在 **策略提示配置 → 策略** 里单独保存；改一个来源不影响其他来源。

## 7. 排障

| 现象 | 检查 |
| --- | --- |
| 消息直接回复、没有工单 | 是否命中 `casual-chat`，或主 Session 判断为普通询问；这是预期行为 |
| 应该接单但被忽略 | 规则是否启用；指令是否足够具体；`eval.mode` 是否为 `observe`（只记录不接单）；是否命中 `needsProject` 反问 |
| 改了规则没有生效 | 是否保存了当前来源自己的规则；是否只是改了安装默认但来源有自己的规则；保存是否因 revision 冲突未成功 |
| 新建工作站没有自动发生 | 现在没有静默建站；需要触发者在会话/面板确认，或按规则提案后确认 |
| 想确认生效规则 | `GET /orchestrator/api/settings` 看 `sources[].policy.rules`、`inherited`；或在面板来源详情看“继承自安装默认”提示 |

## 8. 安全与边界

- 规则是提示词/研判说明，不是权限边界；allowed、admission、Mandate、工具限制才是硬约束。
- 已打开的工作站会话不会因为规则保存而热重建；需要重启或新会话/新 worker 请求才读到新规则（worker 在下一次模型请求生效）。
- 不要把密钥、密码、token 写进规则 instruction；规则会出现在提示词和配置历史里。
- 安装默认与来源规则都是版本化配置，变更会留下历史；运营上建议先用 `observe` 观察规则调整效果，再切 `auto`。
