# 14 P2b 补充实施说明：显式请求的项目归属提问 + folder 回答闭环

> 背景：P2（`d68545d`）把 `needsProject` 只放在 Eval 路径；**显式请求（含全部 folder 投件）未命中项目时仍落 workspace**，与用户要求「识别不出来就反馈该项目没处理过，询问是否新建/给地址」不符。
> 目标：在**不破坏 workspace 临时语义**的前提下，让"命名了未知项目"的显式请求走 `needsProject` 提问；并让 folder 源能闭环回答。

---

## 1. 归属结果三分类（核心规则）

`ProjectService.resolve(trigger)` 除 `project` 外，返回 hints 的**强弱**区分：

| 结果 | 判定 | 处理 |
|---|---|---|
| **命中** | 有 project | 正常建单到该站 |
| **强提示未命中** | 有"强提示"但无匹配 | **needsProject**：拒绝接单 + 提问（不在 workspace 建单） |
| **弱提示/无提示** | 只有文件名等弱提示，或无提示 | 落 workspace（个人临时默认，保持 P1a 语义） |

**强提示**（SourceKind 定义）：
- folder：`PROJECT.md` 的首行（名称/绝对路径/仓库地址），任务名形如 `[项目]xxx` / `【项目】xxx`；
- feishu：会话标题（整体/分词）命中的项目名（P2 已实现，标记为强）；
- github：无（实例默认归属已覆盖）。
**弱提示**：folder 的普通文件名/任务夹名（`hintsOfName` 现有逻辑）——只用于匹配，不触发提问。
- 实现：`ProjectHint` 增 `strong?: boolean`；`SourceKind.projectHints` 返回带标记；`ProjectService.resolve` 返回 `strongHints`（或 `needsQuestion`）供调用方判断。

## 2. 显式接单路径（orchestrator_route accept）

- 解析逻辑不变：`resolve(trigger).project?.id` 命中即建单。
- **新增**：未命中且 `strongHints.length > 0` → 不建单，改记 `needsProject` 决定：
  - 复用 Eval 路径的同一形状：`Decision.kind='stop'`、`reason.code='needsProject'`、`values={candidates, proposal?}`；
  - 通过 `Replies.question` 向触发 Channel 发问（幂等 id `key('question', triggerId)`）；
  - 返回给编排模型的结果明确是「未建单，已向来源提问」，不是静默失败。
  - 建议实现：在 `EngineForMainSession` 增 `askProject(triggerId, {candidates, proposal?})`（内部复用 `Evals.needsProject` 的决策/提问逻辑），或在 `decide` 支持 `kind:'needsProject'`；二选一，保持单一实现、不要复制两份提问代码。
- 弱提示/无提示：维持现行为（workspace），不改既有测试语义。
- 提示词（`prompts/dispatch.md`/`admission.md`）补充：显式请求若点名了未注册项目，必须走 needsProject，不得直接接单。

## 3. folder 源的回答闭环

- **提问落地**：`OutboundMessage` 增可选 `purpose?: 'question'`（仅 `Replies.question` 设置）；folder 的 `channel.send` 在 `purpose==='question'` 时写 `<outbox>/QUESTION.md`（覆盖旧的同线程提问文件），正文头部注明「项目未归属」+ 候选/提案 + 回答方式。
- **回答方式（folder 约定）**：
  1. 把 `PROJECT.md` 写为工作站名称、本地路径或仓库地址，**重新投递**（内容变化即新 hash → 新 Trigger → 重评 → 命中建单）；
  2. 或在面板 `POST /triggers/:id/answer-project`（P2 已有）。
- 问题文本按 kind 增补（`SourceKind.questionHint?` 或 folder channel 自带），folder 文案要写清上述两步；GitHub/Feishu 用各自 @ 语法（P2 已有）。
- 旧行为兼容：无强提示的普通投件仍直接建 workspace 工单，不写 QUESTION.md。

## 4. 测试清单

- `tests/resolve.spec.ts`：强/弱提示区分（PROJECT.md、`[项目]` 名、普通文件名）、命中/强未命中/无提示三分类。
- `tests/runtime.spec.ts` 或新增 `tests/explicit-project.spec.ts`：
  - folder 投件带 `PROJECT.md`（未知站名）→ 不建单、记 needsProject、订单来源出现 `QUESTION.md`；
  - 随后把 `PROJECT.md` 改成已有站名并重投 → 建单到该站；
  - 普通投件（无强提示）→ 仍建 workspace 工单（回归保持）。
- `tests/outbox.spec.ts`：`purpose:'question'` 的 folder 落盘文件名与内容头。
- `tests/panel-server.ts` 类型映射随新路由/字段同步（编译强制）。
- `docs/007` 模块/测试表、`prompts/*` 文案同步。

## 5. 验收

`pnpm check` exit 0；上述场景端到端可测；`plan/13` 的 needsProject 语义在显式与 Eval 两条路径统一（同一 Decision 形状、同一提问实现）；无强提示的临时投件行为不变。
