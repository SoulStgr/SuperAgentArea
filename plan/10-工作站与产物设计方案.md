## 0. 一句话结论

原型把面板从「配置中心」改成「**项目组视图 + 产物反查**」：

- **工单源**是入口：每个监听源（多路径、多仓库、多 IM 渠道）一张卡，卡上是该源的待处理工单与 24h 流水；
- **工作站**是主体：每个项目组一张卡，卡内六段（来源/触发/评估/执行/设置/agent），从项目看全流程；
- **产物**是结果索引：先看到产物，再顺着产物反查「哪个项目 → 哪个工单 → 哪个 assignment → 哪个 worker Session」。

这要求三个领域模型变化：**项目组（Project）成为一等对象**、**来源支持多实例**、**产物有全局索引与反查链**。

## 1. 原型的三个转变（读图结论）

| 原型区域 | 现在（6 Tab 面板） | 目标 |
|---|---|---|
| 左侧导航 | 概览/来源/触发/评估/执行/设置 | **概览 / 工单源 / 工作站 / 提示词 / 策略**（+ 设置齿轮、全局搜索） |
| 工单源卡片 | 「来源」页每源一行 + 折叠列表 | 每个源一张卡：待处理工单、24h 到达/过滤/评估/接单、执行状态；卡片下是该源工单 |
| 工作站卡片 | 无此概念 | 每个项目组一张卡：workspace（固化）+ 工单产生的项目组；六段入口 |
| 产物 | 无界面（只落 outbox 文件 + 结果回复） | 产物直接展示，可反查项目/工单/worker |
| 执行器 | 全局一处在概览/执行页 | 概览保留全局容量；源卡显示该源的工单执行分布（口径待确认，§8-3） |

原型批注里的两条需求即设计约束：

1. 工单源要支持**多路径、多仓库/仓库项目、多 IM（qq/钉钉）、以及阿里云效/私有 Redmine 等外部工单渠道**（接单、创建、修改）→ 来源必须多实例、且 kind 可扩展；
2. 工作站卡片下的工单是「当前源下处理或将处理的工单」——说明工单源与工单是聚合关系，工作站与工单/产物也是聚合关系。

## 2. 领域模型设计

### 2.1 新增对象

| 对象 | 作用 | 关键字段（设计） |
|---|---|---|
| **Project（项目组 / 工作站）** | 持久的工作范围，聚合工单、产物、来源；`workspace` 是固化的默认项目 | `id`、`key`（稳定 slug，如 `aps-填报`）、`name`、`kind: 'workspace' \| 'auto' \| 'manual'`、`address`（本地目录或远程仓库地址，创建工作站时确定）、`directory`（成果落地目录）、`scratch`（副本处理目录）、`sourceIds[]`、`aliases[]`（来源里的项目别名）、`status: 'active' \| 'archived'`、`createdAt`、`lastActivityAt` |
| **SourceInstance（来源实例）** | 同一 kind 的多个监听实例（多文件夹、多仓库、多账号） | `id`（稳定，如 `folder:ops`、`github:zhangsan/aps`）、`kind`、`config`、`enabled`、`label` |
| **Artifact（产物，已有数据、补索引）** | 可直接展示、检索、反查 | 现有：`name/hash/size/at`；新增：`ticketId`、`projectId`、`sourceId`、`deliveredTo`、`messageId`（结果回复）、`createdAt` |
| **ArtifactDelivery（交付记录）** | 产物「投递到哪、何时、是否成功」 | `artifactId`、`channel`、`target`、`messageId`、`dropped?` |

### 2.2 现有对象扩展

| 对象 | 变更 |
|---|---|
| `Ticket` | 增 `projectId`、`sourceId`（反范化，供工单源卡片与项目卡片查询）；**`reporter`（汇报人，默认=触发人）**、`mentions[]`（需要 @ 的人）；`Artifact` 数由索引统计。项目未归属由 Eval 层拒绝（不新增工单阶段） |
| `Trigger` | 增 `sourceId`（实例级，而非 kind）；`meta` 保持源原生字段 |
| `Assignment / Worker` | worker Session 命名已可反查（`worker-<ticketId>`，`src/executor/dsh.ts:24`）；产物 → assignment → session 的链已存在 |

### 2.3 关系

```
SourceInstance 1 ── N Trigger ── N Eval/Decision ── N Ticket ── N Assignment ── 1 Worker Session
                              └──────────────┐
Project 1 ── N Ticket ── N Artifact ── 1 ArtifactDelivery
Project 1 ── N SourceInstance（项目可关联多个源：本地文件夹 + GitHub + 钉钉…）
```

### 2.4 目录模型（v0.2 决策：成果与副本分离）

用户决策：**无项目的临时会话产物落 `workspace`；指定工作站的最终成果落该工作站目录；过程中产生的副本/脚本/日志/固定规则落该工作站同级的「副本处理目录」**。每多一个工作站，主目录下就多一对文件夹。

```
<插件主目录 home>/
├── workspace/                 # 固化：无项目/临时会话的成果落地
│   └── <ticketId>/            # 临时工单工作区与交付
├── <station>/                 # 工作站最终成果（可重命名/归档）
│   └── <产物>                  # 只放最终交付物（可带版本子目录）
└── <station>.work/            # 该工作站的副本处理目录（与 workspace 同级）
    ├── <ticketId>/            # 单工单工作区（隔离，避免并发互相覆盖）
    ├── rules/                 # 固定规则要求（AGENTS.md / 验收口径 / 项目约定）
    └── ...                    # 中间副本、脚本、日志（不交付）
```

- **执行目录**：有工作站 → `<station>.work/<ticketId>/`；无工作站 → `workspace/<ticketId>/`。`Ticket.execution.directory` 记录实际路径，旧工单继续用自己的历史目录（可平滑迁移）。
- **交付**：worker 仍只写工作区内的 `deliver/`；`ready` 时按归属提升——工作站工单 → `<station>/`，临时工单 → `workspace/`；发送源侧仍可收到回执/链接（IM/GitHub），文件夹源收到 outbox 副本。
- **固定规则**：`<station>.work/rules/` 由工作站设置维护（对应"铁定的规则要求"），worker 启动时注入为项目级指令；临时工单不继承（只有全局规则）。
- **主目录口径（已决）**：`areaRoot = <stateDir>/area/`（避免与 DB、worker-bin、session 文件混放）；`work/` 作为旧布局保留只读兼容；副本目录命名（已决）为 `<station>.work/`。

### 2.5 项目归属：在事件源与建单时确定（v0.2 决策）

用户决策：**归属必须在生成工单之前/当时处理，不让工单事后去找项目**。归属解析分三层：

1. **来源实例默认归属**：每个 SourceInstance 可配置默认工作站（例如"钉钉-APS群 → aps 工作站"、"GitHub 仓库 zhangsan/aps → aps"、"文件夹 ops/aps → aps"）。这是最稳定的映射。
2. **事件级提示**：Trigger.meta 携带来源原生线索——文件夹投件里的 `PROJECT.md`（或任务文件夹名）、钉钉消息里的项目名/群标签、GitHub 的仓库与 PR 标签；由 SourceKind 提供 `projectHints(event)`。
3. **解析与匹配**：按工作站的 `name/aliases/address` 做精确匹配（大小写、别名、远程仓库 URL 归一化）。

**归属结果三分支**：

| 情况 | 处理 |
|---|---|
| **明确命中** | 建单时 `ticket.projectId` 直接写入，正常开工 |
| **未命中（不能确定）** | **评估层拒绝并重评**：Decision 记 `stop` + 原因码 `needsProject`，同时向来源会话发一个结构化问题：**"该项目没有处理过。请回复：①新建工作站（给名称）②给项目地址（本地目录或远程仓库）③归到已有工作站（列出候选）"**；回答作为同线程的新 Trigger 进入下一次 Eval，评估通过后建单并绑定项目。面板也可直接回答（`POST /triggers/:id/answer-project`），效果等同在来源里回答 |
| **显式指定**（消息里点名项目或地址） | 先创建工作站（名称 + 本地目录/远程仓库），再建单；成功/失败都回传发送源 |

- **为什么用"拒绝 + 重评"而不是新工单阶段**：不引入新阶段、不改工单状态机；未归属的请求停在 Eval 层，问题与回答都在原线程里闭环，工单从一出生就带着正确的项目归属（正是"不让工单事后找项目"）。
- **新增核心能力**：原因码 `needsProject`（`src/core/reasons.ts` + locales）；回复用途 `question`（面向触发线程的提问，不依赖工单——现有 `attention` 必须挂在工单上）；面板/API 的"未归属问题"列表（有 `needsProject` 决定、尚未回答的触发）。
- **新建工作站**：写 `Project{name, address, directory, scratch}`，自动建 `<station>/` 与 `<station>.work/`（含 `rules/`）；远程地址则在工作区克隆（复用现有 git/gh 环境）。
- **记住映射**：首次在某来源会话里确认归属后，可把"该会话 → 该工作站"记为来源实例默认（面板可改）。
- **通道能力**：`SourceKind.channel` 增 `question(text, people)` —— IM 发消息并 @（飞书/钉钉/QQ）、GitHub 发评论并 @login、folder 源写 outbox 的 `QUESTION.md`，并捕获下一次投件作为回答。
- **来源扩展**：阿里云效、私有 Redmine 等外部工单渠道按 SourceKind 扩展（事件→Trigger，支持接单/创建/修改），归属规则同上。

### 2.6 汇报人与提及（v0.2 决策）

用户决策：**每张工单必须有汇报人，默认是发布者；用户特别指定的人（如"小C 到时候看看"）要进入 @ 提及，并在建单后把工单详情回传发送源**。

- `Ticket.reporter`：默认 `= trigger.actor`；可在建单时由决定覆盖。
- `Ticket.mentions[]`：评估阶段从对话内容提取（示例：经理 A 发布任务后说"小C 到时候看看"→ 提及小C）；`accept` 决定新增 `mentions` 字段（可空）。
- **校验**：提及对象必须是该 Source 认识的人（允许名单/成员目录/机器人名单），否则丢弃并在 Decision 的 reason 中记录"未知提及"。
- **回传**：建单后向发送源发一张结构化"工单卡"（id、标题、项目、汇报人、状态、链接）+ **@ 汇报人 + @ 提及人**；后续 `ready / blocked / failed / attention` 同样回传并 @。
- **通道实现**：`SourceKind.channel` 增 `mention(person): string`——飞书 `<at>`、钉钉 `@userId`、GitHub `@login`、文件夹写 `REPORT.md` 的"汇报人/提及"行；无 @ 能力的源降级为纯文本署名。
- 跨源不映射身份（沿用现状）；同一个人在不同源是不同 `PersonRef`。

## 3. 信息架构

### 3.1 导航

```
SuperAgentArea
├─ 概览 Overview            （默认）
├─ 工单源 Sources            （新：多实例源卡片 + 该源工单 + 未归属问题）
├─ 工作站 Workstations       （新：项目组卡片 + 项目内六段）
├─ 提示词 Prompts            （由设置提升为一级）
├─ 策略 Policy & Eval        （由评估页 + 设置合并提升为一级）
├─ 全局搜索（顶栏，常驻）      （工单/线程/触发/产物/链接）
└─ 设置（齿轮，非 Tab）       （执行器/执行环境/部署/多源配置/凭据）
```

### 3.2 每页信息块

**概览**
1. 需要我处理（跨项目工单，带回答/重试/停止动作）
2. **最近产物**（名称、项目、来源、时间；点开产物详情 → 反查链）
3. 系统健康与队列（全局执行器：执行中/排队/等待触发；各源状态点）
4. 24h 流水（到达/过滤/评估/接单/产物）

**工单源**
- 每个 SourceInstance 一张卡：
  - 标题（可读 label + kind 图标）、状态点、启用开关
  - **待处理工单 N**（无则"没有待处理的工单"）
  - **过去 24 小时**：到达 / 被过滤 / 已评估 / 接单或忽略
  - **执行状态**：该源工单的「执行中 / 排队 / 等待触发」（口径见 §8-3）
  - 卡片下方 = 该源工单列表（沿用现有 TicketLine，支持过滤）
- 页头动作：**添加来源**（多实例；kind 选择器：文件夹/GitHub/飞书/钉钉/QQ/…
- 空态：没有任何源时，引导"添加第一个来源"，而不是空白

**工作站**
- 卡片：项目名、**地址类型**（本地目录/远程仓库）、来源数、工单数/进行中数、产物数、**最近汇报人**、最近活动时间；卡内六段按钮 `来源 | 触发 | 评估 | 执行 | 设置 | agent`
- `workspace` 固定在首位（固化的临时工作区；无项目工单的成果落点）
- 点卡片 → 项目详情（六段），点按钮 → 该段的项目级视图
- 页头动作：新建工作站（名称 + 地址）/ 归档 / 显示已归档；**未归属问题**（`needsProject` 决定的提问）在此页顶部提示，可在此直接回答

**项目详情（六段，页内分段而非叠 Tab）**

| 段 | 内容 |
|---|---|
| 来源 | 该项目关联的源实例 + 最近投件；可关联/解除关联 |
| 触发 | 该项目的线程列表（过滤：订阅/评估中/24h/全部） |
| 评估 | 该项目的决定（强度、规则原因、方向证据、策略版本） |
| 执行 | 该项目的工单（阶段、派工、产物数）、暂停/重试/停止 |
| 设置 | 项目级配置（成果目录、副本处理目录、固定规则 `rules/`、验收口径、提示词覆盖、模型） |
| agent | **项目 Session**：点击打开该项目的会话（弹窗/面板内），展示该项目触发的**工单历史**与**修改历史**（产物版本、结束结果、派工次数）；会话本身可继续对话 |

**产物详情（从概览/项目/工单任一处进入）**

```
产物卡：名称 · 大小 · hash · 项目 · 来源 · 时间 · 汇报人
  └─ 反查链：Artifact → Ticket → Assignment → Worker Session（可打开）
             └─ 落点：工作站成果目录 <station>/ 或临时 workspace/（副本处理目录不展示）
             └─ 交付记录：结果回复、发送源回执、是否成功
             └─ 下载 / 复制路径
```

### 3.3 与现有 6 Tab 的对应（保留/合并/删除）

| 现有 | 去向 |
|---|---|

## 4. 产物 → Worker 反查（核心链路）

**数据链（已具备）**：`Artifact`（`KV.artifacts(ticket)`，`src/kv.ts:66`）→ `Ticket`（`ticketId`）→ `Assignment`（`ticket.assignments`）→ `workerSessionId = worker-<ticketId>`（`src/executor/dsh.ts:24`）。

**要补的**：
1. 产物索引表/家族（全局列出）：`artifact:{id}` + 查询（project、source、ticket、时间、名称/哈希）；
2. 反查 API：`GET artifacts/:id` 返回 `{ artifact, ticket, assignment, workerSessionId, project, delivery }`；
3. 产物卡片上的「打开 worker」：调用 DSH 打开该 Session（现有 `ctx.uiWorkspace.openSession`，`src/client/index.tsx:38`），并在 Session 内定位到该 Assignment 的 report（可选）；
4. **落点与排除**：artifact 记录 `targetRoot`（`<station>/` 或 `workspace/`）；`<station>.work/` 下的副本/脚本/日志**不是产物**，不进索引、不交付；结果回复里给出落点路径；
5. **项目历史投影**：项目 Session 展示的「工单历史 + 修改历史」由 `tickets`（阶段/报告/结束）+ `artifacts`（版本/哈希/落点）+ `assignments`（派工次数）派生，不新增独立历史存储。

**「先给产物再反推」的两种入口**：
- 概览「最近产物」→ 详情 → worker；
- 工作站卡片 → 产物数 → 该项目产物列表 → 详情 → worker。

| `artifact` 表 | 替代/镜像现有 `KV.artifacts(ticket)`；字段见 §2.1，另加 `targetRoot`（station/workspace 落点）；按 project/source/ticket/时间建索引 |

| `source instance` 配置 | 设置结构从 `sources[kind]` 变为 `sources[instanceId]`；新增 `defaultProjectId`（来源实例默认归属）；迁移：旧 `sources[kind]` → 实例 id=kind |
| 目录布局 | 新 `areaRoot`：`workspace/`、`<station>/`、`<station>.work/`（§2.4）；旧 `stateDir/work` 只读兼容 |

### 5.2 API

```

GET  /projects/:id                → { project, sources, tickets, artifacts(摘要), stats }
```

## 8. 决策记录与剩余待确认

### 8.1 已决策（2026-11-25，来自用户）

1. **归属时机**：在事件源/建单时确定项目，不让工单事后反查；未识别时向发送源提问"新建工作站 / 给项目地址（本地或远程仓库）/ 归到已有"。
2. **目录模型**：workspace = 插件主目录下的固定工作区；每多一个工作站，主目录下多一个成果目录 + 一个同级副本处理目录；成果落工作站，副本/脚本/日志/固定规则落副本目录。
3. **多实例**：本期做 folder + GitHub 多实例（多路径/多仓库/多账号）；IM 与其他渠道随后。
4. **项目 agent**：点击打开**项目 Session**，展示该项目触发的工单历史与修改历史。
5. **产物落点**：临时/无项目 → `workspace/`；指定工作站 → `<station>/`；中间文件/日志/技能文件 → `<station>.work/`（不交付）。
6. **汇报人与提及**：工单必须有汇报人（默认发布者），用户特别指定的人进 @ 提及；建单后把工单详情回传发送源并 @ 相关人。

7. **主目录口径**：`<stateDir>/area/`（避免与 DB/worker-bin/session 文件混放）。
8. **副本目录命名**：`<station>.work/`。
9. **归属阻塞形态**：**评估层拒绝并重评**（不新增工单阶段；Decision 记 `stop` + `needsProject`，向来源提问，回答作为新触发重评）。
10. **Prompts/Policy 位置**：**提升为一级页**（设置齿轮只留执行器/执行环境/部署/多源配置/凭据）。
