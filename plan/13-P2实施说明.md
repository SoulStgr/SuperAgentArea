# 13 P2 实施说明：项目归属前置 + 汇报人/@提及回传

> 前置：P1a（数据模型，`47c7db6`）、P1b（多实例来源，见 [12-P1b多实例实施说明.md](12-P1b多实例实施说明.md)）。
> 设计依据：[10-工作站与产物设计方案.md](10-工作站与产物设计方案.md) §2.5/§2.6、[11-P1数据模型与接口设计.md](11-P1数据模型与接口设计.md) §5/§6。
> 范围：**归属解析 + `needsProject` 拒绝回环 + 汇报人/提及 + 建单回传**；不做工单源/工作站页面（P3/P4），不做产物 UI（P5）。

---

## 1. 归属解析（在评估/建单时，不让工单事后反查）

解析顺序（第一个命中即用）：

1. **来源实例默认归属**：`settings.sources[instanceId].defaultProjectId`（P1b 已留字段）。
2. **事件提示**：`SourceKind.projectHints?(trigger, config): ProjectHint[]`——`ProjectHint = { name?: string; path?: string; url?: string }`：
   - folder：任务文件夹里的 `PROJECT.md`（首行项目名/地址）、任务夹名（若形如 `[项目]xxx` 或与工作站别名匹配）；
   - github：仓库→工作站的显式映射（来源实例默认归属即可覆盖），以及 PR/Issue 标签（可选，P2 先不读标签）；
   - feishu：会话/群的项目别名（P2 用会话标题匹配别名即可）。
3. **工作站注册表匹配**：按 `Project.key/name/aliases` 精确匹配（大小写不敏感、去空格）；folder 的 `path` 与 `Project.location.path` 归一化后比较；repo 的 `url` 归一化比较。
4. **未命中** → 进入 §2。

命中后：`ticket.projectId = project.id`、`ticket.sourceId = instanceId`；输出目录/副本目录按项目取（P1a 已支持 workspace；P2 支持 station 目录）。

## 2. 未命中：Eval 拒绝 + 提问 + 回答重评

- **决定**：`Decision.kind = 'stop'`，`reason.code = 'needsProject'`，`reason.values = { candidates: [{id,name,kind}], proposal?: { name, location } }`；不建工单。
- **提问**：向触发所在会话发一条结构化问题（见 §3 的 `question` 回复用途），文本由系统生成：
  "该项目没有处理过。请回复：①归到已有工作站（列出 candidates）②新建工作站（给名称与地址：本地目录或仓库）③确认建议（若有 proposal）"。
- **回答**：
  - 来源会话里的回答作为同线程新 Trigger → 下一次 Eval 解析项目 → 命中则建单；
  - 面板回答：`POST /triggers/:id/answer-project { projectId } | { new:{name,location} } | { confirmProposal:true }`——P2 实现该路由（鉴权：面板同源 + loopback，沿用 http.ts 模式）。
- **提案（agent 建议 + 人确认）**：评估模型可给出 `proposal`（存在 `needsProject` 的 values 里）；只有人确认（面板 confirmProposal 或来源里明确回复确认）后才创建 Project。**模型不得直接建站**。
- **回答后的重评**：由现有 `reevaluate`/同线程新 Trigger 机制驱动；不要新增工单阶段。

## 3. 核心新增能力

| 能力 | 落点 | 说明 |
|---|---|---|
| 原因码 `needsProject` | `src/core/reasons.ts` + locales（中英） | 面板/日志可读 |
| 回复用途 `question` | `src/core/replies.ts` 的 `ReplyRequest` + `Replies` | `{ purpose:'question', triggerId, text }`；channel 取 triggering 的 channel；id = `key('question', triggerId)` 幂等；不依赖工单（现有 `attention` 必须挂工单） |
| 渠道提问/提及 | `SourceKind.channel` 增 `question(text, people)` 与 `mention(person)` | 默认实现：`mention` 返回空串（无 @ 能力），`question` 复用 `send`；GitHub：评论 + `@login`；Feishu：`<at id>`；folder：写 `<outbox>/QUESTION.md`（下一次投件即回答） |
| 项目提示 | `SourceKind.projectHints?` | folder 读 `PROJECT.md` 与名称；其他 kind 先返回空（默认归属已覆盖） |
| 汇报人/提及提取 | `accept` 决定增 `reporter?`、`mentions?: PersonRef[]` | 汇报人默认触发 actor；提及从对话提取（"小C 到时候看看"），**校验**：必须是该来源认识的人（policy allowed + 来源成员目录；folder 的 operator；GitHub 的 allowed login；未知提及丢弃并在 Decision reason 记 `unknownMention`） |
| 建单回传 | 接受后向来源发"工单卡" | 文本含：工单 id/标题/项目/汇报人/阶段/链接；`mentions` 通过 `channel.mention` 渲染；**@ 汇报人 + @ 提及人**；结果/阻塞/提问同样带 @（复用同一渲染函数） |

## 4. 数据与 API

- 无新表；`Ticket.reporter/mentions` 已在 P1a 落库；`Decision.reason.values` 存 candidates/proposal。
- `POST /triggers/:id/answer-project`（P2 实现；P3 面板接入）：请求体三种形态；返回 `{ resolved: projectId }` 或错误 `projectLocationInvalid`/`projectUnknown`/`projectSpecifiedByModel`。
- `GET /sources`（P1b 后）已按实例；P2 增 `pendingProjects`（该实例下 `needsProject` 未回答的触发/线程）供 P3 页面用（视图字段，不新建页面）。

## 5. 安全与校验

- 外部地址只能由**人**给出或确认；`answer-project` 走面板同源校验；来源里回答的人必须是 policy 允许的人（复用现有 gate）。
- 路径校验：绝对路径、存在或可创建、可写、非系统保留目录（`C:\Windows`、`/etc` 等）；仓库地址校验协议（https/ssh/file）与克隆权限。
- 提案确认记录 `specifiedBy`（提案人）与 `confirmedBy`（人）。

- `tests/runtime.spec.ts`：未命中 → 提问 → 回答 → 重评 → 建单（含面板 `answer-project` 路径）；提案确认后才建站；未知提及被丢弃。

- `docs/007-architecture.md` 模块/测试表同步。

## 7. 验收

`pnpm check` exit 0；以下场景端到端可跑：
1. 默认归属命中：来源实例配置了 `defaultProjectId`，投件直接建单到该站；
2. 未命中：收到提问 → 在面板回答"归到 X" → 重评 → 建单到 X；
3. agent 提案：评估给出 proposal → 人确认 → 建站 → 建单；
4. 建单回传：来源里收到工单卡，@ 了汇报人与提及人（folder 源写文件、github/feishu 用各自 @ 语法）。
