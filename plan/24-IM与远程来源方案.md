## 1. 关键发现：dsh-im 已具备现成连接层

本机 profile 已安装 `@xmanrui/dsh-im 5.10.0`，它提供：

- **九渠道账号管理**：微信（扫码）、飞书、钉钉、企业微信、企业微信应用、QQ、Telegram、Slack、Discord、WhatsApp；每渠道多机器人，各自连接/工作区/模型/会话独立。
- **出站主动投递 `ctx.dshIm`**：`send(botId, targetId, text, {format})`、`listBots()`、`describeBot(botId)`、`listTargets(botId)`、`createTarget(botId, …)`；HTTP `POST /api/dsh-im/delivery/messages`、Connection RPC `message.send`。九渠道全部支持。
- **入站外部消费 `consumeInbound(botId, {expectedFingerprint, onEvent})` + `replyChecked`**：版本 1 事件含 `channel/botId/fingerprint/eventId/messageId/actor/conversation/mentions/text/reply`；回复按原消息校验（防串会话）；**目前仅飞书/Lark**（opt-in，`consumerMode: 'external-consumer'`；其他渠道保持 dsh-im 自带会话桥）。
- 依赖里已有 `dingtalk-stream`、`@tencent-connect/qqbot-connector`、`@wecom/aibot-node-sdk`、`imapflow` 等成熟 SDK。

**结论：不要重写协议。** 钉钉/QQ/微信的账号、扫码/凭据、长连接、AI Card、文件与图片能力优先复用 dsh-im；缺的是**非飞书渠道的入站消费者接口**。

## 2. 三条入站路径与选择

| 路径 | 做法 | 优点 | 风险/成本 |
|---|---|---|---|
| **A. 扩展 dsh-im（推荐）** | 给 dsh-im 的 external-consumer 增加 dingtalk/qq/wechat 支持（其 `src/channels/<ch>/` 已有连接与消息解析，只需在控制器上暴露同形状事件与 `replyChecked`） | 复用成熟连接、扫码、多机器人、AI Card；SuperAgentArea 只写一个通用桥 | 需改第三方包（上游 PR 或本地 patch）；三家工作量集中在 dsh-im |
| **B. 原生适配器** | 我们直接依赖 `dingtalk-stream`、`qqbot` SDK 实现收发 | 不依赖 dsh-im 改动 | 钉钉卡片/重连/权限、QQ 私聊/群聊、文件图片都要重做；微信个人号 iLink 协议非公开，基本不可行 |
| **C. 会话级桥接** | 把机器人聊天绑到 SuperAgentArea 专用 DSH 会话，监听会话消息 | 不改 dsh-im | 会与 dsh-im 自身回答重复；无法稳定拿到结构化事件；不采用 |

**决定**：
- 钉钉、QQ：优先 A；若上游短期不可用，再为钉钉做 B（Stream SDK 已具备），QQ 仍等 A。
- 微信：只能 A（iLink 为 dsh-im 内部实现，且个人号自动化有账号风险；方案里默认关闭群自动回复、仅白名单私聊）。
- 飞书：已有独立 `feishu` kind（bot CLI），保持现状；未来可选切到 dsh-im 的飞书消费者，二选一避免双收。

## 3. SuperAgentArea 侧的统一桥设计

新增 `dsh-im` 源族（三个 kind：`dingtalk`、`qq`、`wechat`，共用一套桥）：

- **账号 = dsh-im 机器人**：配置 `{ botId, conversation?: 'dm'|'group'|'all', requireMention?: true, allowed?: [...] }`；从 `ctx.dshIm.listBots()` 选择，避免重复录入凭据（凭据只在 dsh-im 保存）。
- **健康**：`describeBot(botId)` 的 online/offline + `consumeInbound` 注册状态；每账号独立条目。
- **入站**：`consumeInbound(botId, { expectedFingerprint, onEvent })`：
  - 过滤：conversation 类型、是否 @、发送者白名单；
  - 去重：`eventId`/`messageId` 写入 KV（保留 7 天）；
  - 归一化 Trigger：`source = <kind>:<instance>`，`thread = <kind>:<botId>:<conversationId>[:<threadId>]`，`text` 原文，`meta` 带 actor/conversation/reply 路由（不透明 token，不入日志）；
  - 授权：只有白名单人类可发起；机器人/自己消息不授权（与现有规则一致）。
- **出站**：`replyChecked(botId, event.reply, text, { expectedFingerprint })`；文件/图片后续用 dsh-im 的附件能力；失败重试与 `reply-result-unknown` 语义按 dsh-im 契约，不盲目重发。
- **会话/工单**：沿用现有 Trigger→Eval→Ticket→Worker；汇报人 = IM 发送者，@ 用渠道原生语法（dsh-im 事件给 mention 列表）。
- **降级**：dsh-im 不可用/未装时，kind 显示「需要 dsh-im」并保持 paused，不阻塞其他来源。

## 4. 远程文件夹（SSH/SFTP）——本轮实现

新增 kind `remote`（远程文件夹），与本地文件夹同构的投件/回执模型，传输走 SFTP。

**配置**：`host`、`port`(22)、`username`、`identityFile`（私钥路径）、`knownHosts`（known_hosts 文件路径）、`hostKeySha256`（可选指纹钉死）、`inbox`、`outbox`（远端绝对路径）、`pollSeconds`(30)、`maxFileBytes`(1 MiB)、`operator`。

**安全要求（硬性）**：

1. **只用密钥认证**：`BatchMode=yes`、`IdentitiesOnly=yes`、不存密码、不读 ssh-agent（显式 `-i`）。
2. **主机密钥强校验**：`StrictHostKeyChecking=yes` + `UserKnownHostsFile=<配置>`；缺失/不匹配即报错暂停，**绝不** `accept-new`；可选 `hostKeySha256` 再做一次指纹比对。
3. **不执行 shell**：只用 `sftp -b -` 批处理（`ls/get/put/rename`），路径限定 `[A-Za-z0-9._/-]+`，拒绝 `..`、换行、引号、通配符；inbox/outbox 必须是绝对路径。
4. **限额**：单文件 ≤ `maxFileBytes`，每轮最多 20 个文件；超时（连接 15s、单命令 30s）；失败按现有连续失败阈值进 health。
5. **最小权限**：远端建议专用只读写目录、专用 key（`command=` 限制可选）；文档给出 sshd 最小配置示例。
6. **本地临时文件**：写入 `<stateDir>/area/remote.tmp/<instance>/`，处理后删除；不落长期副本。
7. **幂等**：处理后 `rename` 到 `inbox/.done/`；回复文件写 `outbox/<messageId>.md`，重试用同名覆盖。

**流程**：`ls inbox` → 跳过 `.done`/隐藏/超限 → `get` 到临时目录 → 解析为 Trigger（`source=remote:<instance>`，`thread=remote:<instance>:<file>`，汇报人=operator）→ 工单完成 → 回执 `put` 到 outbox → 源文件 `rename` 入 `.done`。
