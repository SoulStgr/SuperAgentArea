## 1. 需求与结论

**需求**：多平台监听（QQ/微信、钉钉、远程文件夹、本地文件夹、飞书、各种代码仓库），交付形式不定（可能只是回答，也可能是文件输出）；按《Superagent融合架构》把 T0–T5 生产线装进 Super-agent。

**一句话结论**：原型已经把融合文档 **L1 Router 层做完了大半**（Trigger 归一化、Fast/Slow Path、Ticket/Mandate、Thread Subscription、独立 Session/目录、持久化恢复、幂等 Outbox、面板），改造重心是：

1. **L0 源扩展**——用官方 `SourceKind` 扩展点接入新平台（侵入最小）；
2. **交付扩展**——新增 Artifact 模型与文件输出通道（回答 ≠ 只有聊天回帖）；
3. **L2 生产线**——用 prompts/skills 把 Worker 塑造成"理解→规划→dry-run→特性分发→并行验收"；
4. **治理与 L3**——Watchdog 门禁、Mandate 预算/租约、安全加固、知识池（后置）。

## 4. L0 事件源扩展设计

所有新源实现同一契约 `SourceKind`（`src/sources/kind.ts`）：`schema/fields`（配置与表单）、`scope`（接收范围）、`channel`（幂等回帖）、`threadContext`（评估上下文）、`policy`（授权名单/admission 行）、`environment`（worker 变量）、`health`。注册进 `SourceRegistry`，加 tsdown 入口 + `cordis.patch.yml` insert（默认 disabled）。教程：`docs/008-cookbook.md`。

与原型的差异说明：GitHub/飞书源走 **CLI 子进程**（gh / lark-cli）；新源允许**进程内直接 HTTP/SDK**（钉钉 Stream、S3 SDK 等），只要遵守同样的幂等/健康/中止纪律。凭据一律走配置/环境变量，不进 Trigger/meta。

### 4.1 阶段1：本地文件夹源 `folder-watch`（详设）

**目录约定**（每个配置行一个实例）：

```
<inbox>/                      投件区：新文件/新任务文件夹 = 新任务
  ├─ 报告.xlsx                 单文件任务
  └─ fix-login-bug/            任务文件夹
       ├─ TASK.md              任务说明（作为 Trigger 正文）
       └─ 附件…
<outbox>/                     交付区
  └─ <ticketId>/
       ├─ <messageId>.md       回复文件（幂等键 = 消息 id）
       └─ artifacts/…          产物文件（§5）
```

**域映射**：

| 概念 | 映射 |
|---|---|
| Trigger | 一个投件（文件或任务文件夹的一次有效版本） |
| Trigger id | `key('folder', <rowId>:<相对路径>:<内容hash前16位>)`——编辑产生新事件，重读幂等 |
| Thread | `folder:<rowId>:<任务键>`；任务文件夹内追加文件 = 同 Thread follow-up（直通 Worker） |
| Actor | 配置的操作者 id（默认 OS 用户名），`human: true`，`addressed: 'direct'`（投件即显式下达） |
| Channel | 回复写到 `<outbox>/<ticketId>/<messageId>.md`；`allowed` 检查配置行仍在 |
| 接收范围 | 每个 inbox 一行 admission；默认只收操作者投件 |

**关键机制**：
- **写完整性**：轮询扫描（默认 10s），文件需连续两轮 size/mtime 不变才视为投件完成，避免读到半截文件；
- **cursor**：`KV.folder.cursor` 记录已处理投件集合/水位，`receive` 成功后才推进；中断重放安全（稳定 id 去重）；
- **任务文件夹**：以 `TASK.md` 正文为 Trigger text，附件清单进 `meta.files`；无 TASK.md 的文件夹以文件夹名 + 文件清单为 text；
- **环境变量**：`DSH_SUPERAGENT_FOLDER_INBOX/OUTBOX/TASK`，worker 据此读附件、写 `deliver/`；
- **health**：`folder` 条目；目录不可读连续 3 轮报 error；
- **测试**：翻译/去重/scope/写完整性/幂等 send/cursor 中断/插件注册与中止，按 cookbook §11。

### 4.2 远程文件夹：`sftp-watch` 与 `s3-watch`（阶段2）

- **sftp-watch**：SSH 轮询远端目录列表（size+mtime 水位），下载到 ticket 目录再投件；回复/产物上传回远端 outbox。凭据：密钥路径/ssh-agent，配置存引用不存内容。复用 folder-watch 的域映射与写完整性逻辑（抽公共 `folder-core`）。
- **s3-watch**：轮询 bucket prefix（或接事件通知），ETag 作稳定 id；交付 = 上传产物 + 预签名 URL 进回复。S3/OSS/MinIO 同一 SDK 风格，endpoint 可配。
- 两者与 folder-watch 共享"投件→任务→交付区"语义，面板体验一致。

### 4.3 钉钉源 `dingtalk-watch`（阶段2，IM 里最规范）

- 企业内部应用机器人，**Stream 模式**（WebSocket 长连接，无需公网 IP）收群聊 @/单聊消息；回复走机器人发消息 API（带幂等键）。
- Thread = 会话 + 话题；actor = 钉钉 userId；allowlist 按 userId；`threadContext` 读会话历史（API 受限，先给触发消息上下文）。
- 需要：企业管理员建应用、AppKey/AppSecret、机器人进群。

### 4.4 QQ 官方机器人源 `qqbot-watch`（阶段2，已选主路线）

- q.qq.com 开放平台：WebSocket 事件网关收群 @/频道消息，被动回复有**时效窗口**（超时需主动消息权限）；沙箱环境先验证。
- Thread = 群/频道 + 消息话题；actor = openid；allowlist 按 openid。
- 风险：群 bot 审批门槛、被动回复窗口限制 → Outbox 重试策略要适配"窗口已过"错误（按 `gone`/降级处理）。
- 需要：平台认证、AppID/AppSecret、目标群/频道白名单。

### 4.5 代码仓库源（阶段3）

- **GitLab/Gitee**：API 风格接近 GitHub，把 `github-read/github-trigger/github-pull` 抽成平台无关的 `git-platform` 层，各自实现 REST 适配；PR/MR 生命周期绑定 Ticket 完成（`bindThread/threadClosed`）照搬。
- **本地/局域网 git**：无平台 API → folder-watch 变体 + git CLI；监听分支/工作区变化，交付以 **patch 文件/分支推送**为主，回帖走 outbox 文件。
- **多仓库核心改动**：`deployment.ts` 的单 `repository` 下放到各 Source 实例配置；Setup 按实例探测账号；Mandate 的 scope 按工单来源仓库计算。这是阶段3唯一必须动核心的点。

### 4.6 QQ/微信接入路线对比（待决策）

| 路线 | 原理 | 优点 | 缺点/风险 | 实现成本 |
|---|---|---|---|---|
| **QQ 官方机器人**（已选） | 开放平台 WS 网关 | 官方合规、不封号 | 群 bot 审批严、被动回复时效窗口、沙箱限制 | 中 |

## 5. Artifact 与文件输出设计（阶段1）

**原则**：交付 = 回复消息 + 产物清单；产物是一等公民，可索引、可追溯、幂等交付。

- **产物约定**：worker 把最终交付物写进 ticket 目录的 `deliver/`（准备命令/environment 告知路径）；
- **登记**：worker 报告 `ready` 时，Executor 扫描 `deliver/`，为每个文件生成 Artifact 记录 `{path, hash, size, summary?, ticketId, at}` 写入 Store（新增 `artifacts` 表，KV 键进注册表）；
- **交付**：delivery 步骤把产物复制到目标交付区——folder/sftp/s3 源 → 各自 outbox/artifacts；IM 源 → 发文件消息（平台支持时）或附下载链接/路径；
- **回复**：结果消息列出产物清单（名称/路径/hash 摘要），聊天回复与文件交付**同一条 Outbox 事务**，保证幂等一致；
- **面板**：Ticket 视图加产物列表（阶段1 先文本清单，后续卡片）；
- **后续演进**（阶段3+）：`orchestrator_deliver` 工具让 worker 主动登记带摘要的产物；Artifact 进 Chain of Recall 与知识池回填。

阶段1 用"约定目录 + ready 时扫描"实现，**不加新工具面**，把改动压在 executor 与 Store，风险最小。

> **实现状态（2026-11-24）**：已落地。`src/sources/folder.ts`（folder Source，9 个测试）、`src/app/artifacts.ts`（收集/幂等拷贝/结果回复，5 个测试）、`src/kv.ts` 的 `folder`/`artifacts` 键族、bundle 内 `dsh-superagent-folder` 条目、worker 提示词中的 `deliver/` 约定。挂点：`orchestrator_report` 在 `ready` 时入队 `artifacts` 效果 → `DshExecutor` 处理。

## 7. 治理层（阶段4 概要）

- **Watchdog 四门禁**：无进展（步数/token/时长停滞）、循环（重复工具调用指纹）、偏航（产物偏离验收/超 Mandate）、预算（超限熔断）。信号取自 session 事件流（`sessions.ts` 已有订阅骨架）；动作分级：确定性重试→语义重试（换方案）→换 Worker→降级→人工，**分开计次留痕**。
- **Mandate 预算/租约**：Mandate 增 `budget{tokens, duration, attempts}` 与 Assignment `lease`；Engine 在 report/turn 事件处核销。
- **安全加固**（融合文档 §7）：写盘前 fail-closed 闸（未授权路径 BLOCK）、worker 沙箱/独立身份评估、凭据按 ticket 短期发放、append-only 审计表（谁授权/谁执行/动了什么）。
- 主动模式三档 `off/observe/auto` 对齐现有 Policy 的 proactive 记录模式，`auto` 加"规则命中+预算内+可回滚"三条件。

## 8. L3 知识池（阶段5 概要）

- `KnowledgeEntry{type, sourceTicket, evidence, confidence, tags, expires}` 新表 + 归档回填管道（ready/验收后触发：去重/归并/打证据/设有效期）；
- 读出：规划中枢检索 → 摘要/引用 Inline，全文 Spill；
- 运行态（Store/session）与沉淀态（知识池）分离，沿用融合文档 §6 双层表。

## 10. 风险与反模式

- 沿用融合文档 §11 全部反模式（Router 不做业务大脑、上下文不塞全量、面板不当流程节点、无授权不开 auto、Worker 不共享目录、特性粒度可验收、监控必须做门禁）；
- **版本漂移**：0.2.1-alpha.2 → 0.2.2-rc.5 的 API 变化在阶段0/部署冒烟暴露，逐项记录修复；
- **IM 风控**：个人号桥接路线封号风险显式告知，默认不启用；
- **上游不更新**：原型是静态快照，所有演进由本仓库承担，不期待上游修复；
- **范围控制**：阶段1 严格只做 folder-watch + Artifact，其余源不提前动工。
